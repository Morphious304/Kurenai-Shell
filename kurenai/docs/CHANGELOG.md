## Fixes and additions after the first Settings release
- Fixed: **KURENAI Settings did not open from Rofi** ("Failed to execute: 'kurenai-settings' ... No such file or directory"). The application entry said `Exec=kurenai-settings`; Rofi starts entries without `~/.local/bin` on its PATH. The entry now holds the absolute path and is written by `kurenai-ctl desktop-entry install` (the installer runs it). `validate` flags a relative entry. On an installed system: `kurenai-ctl desktop-entry install`.
- Fixed: **`kurenai-hypr.lua` "is not installed"** when running `kurenai-ctl enable-hypr`. That file is generated by `kurenai-hypr apply`, so it did not exist before the first apply. The installer now puts a comment-only placeholder there (never over an existing file) and `enable-hypr` creates it itself if missing; the placeholder changes nothing until you apply.
- New: a **Settings** tile in the quick settings panel (next to App colours). It opens the window even if `~/.local/bin` is not on the shell's PATH.
- Fixed (root cause, found by running the shell in a real Quickshell 0.3.2 built from your source, under a headless Wayland compositor): **notification popups never appeared** even though the shell received the notification (the bell counted it). The popup window was only made visible "when its own list has items", but a hidden window never builds its list, so it could never become visible. It is now shown when the notification store has popups, and the cards sit in a Column (the old ListView stacked new cards on top of each other). Checked: normal, low and critical popups stack top-right under the bar, low and normal time out, critical stays.
- New (safety net, separate from the fix above): the shell can also tell when another program (mako, dunst, swaync) owns the notification service. The shell now checks who owns it and shows a banner in the notification centre with a one-click "Show notifications here instead" (stops that daemon, restarts the shell; undo `kurenai-ctl notif-restore`). New `kurenai-ctl notif-test` sends a low, normal and critical notification and says who owns the service; `notif-status` also lists D-Bus auto-start files; the Settings Notifications page has a "Send test notifications" button. Not run in a real Quickshell: if popups still do not appear with the banner absent, send me the output of `kurenai-ctl notif-test` and `kurenai-ctl logs`.
- New app colours: **pacsea** and **lazygit** (`kurenai-ctl theme extra pacsea on`, `... lazygit on`; also in Settings > App colours). Checked against their documentation and in a throwaway home with stand-in programs; not run in the real apps.

## Glass, second version: fixes a freeze
- **Fixed:** the first `kurenai-glass.lua` loaded the plugin (`hl.plugin.load`) while Hyprland was still reading its config. hyprglass documents that route as able to stop Hyprland from finishing its start, and on a real machine it froze the system. The module now loads the plugin AFTER Hyprland is ready, from the `hyprland.start` event, through the new `kurenai-glass-start` (it does what `hyprpm reload -n` does by hand, then re-reads the config). The old route stays as `LOADER = "config"`, opt-in.
- New: a safety net. If a start with glass does not reach 30 s, the next start switches glass off by itself (`glass.disabled`), notifies you, and `kurenai-ctl glass-reset` turns it back on. `kurenai-ctl glass-status` now shows loader mode, safety state, the start log and `hyprpm list`.
- `install.sh` REPLACES the first version of `kurenai-glass.lua` (it has no `LOADER` line), keeps your old copy in the backup folder and carries over `PROFILE = "lite"`.
- Not verified: the plugin itself (no GPU here), and that loading during the config read is the cause on your machine (inferred from the plugin's docs and from `hyprpm reload` working). See [docs/GLASS.md](GLASS.md).

## Glass (hyprglass plugin), optional
- New: `kurenai-glass.lua` + `kurenai-ctl enable-glass` / `disable-glass` / `glass-status`. One marked line in `hyprland.lua` LOADS the plugin at every login (from where hyprpm built it) and applies KURENAI's glass settings (your clear/contrasted presets kept, a new `kurenai-panel` preset, the shell's layers by exact name, `PROFILE = "lite"` for a lighter GPU load). Why the plugin did not start by itself before, and how to set it up: [docs/GLASS.md](GLASS.md).
- New setting `glassOpacity` (Bar and panels, default 100 = unchanged): below 100 the bar and panels become translucent so glass shows through. The bar background moved from the window colour to a rectangle, because a window decides whether it has an alpha channel when it is created, before the settings file is read.
- Checked: option names against the plugin's source, the module in the real Hyprland 0.57.0 Lua engine (`--verify-config`), hook/status/rollback in a throwaway home, the shell rendering translucent in a real Quickshell. **The plugin itself was not run** (no GPU here), so the look is untuned. See GLASS.md, "Verified, and not".

## 4a.5: grey screen / "locker thinks it is locked"
After an unlock, the locker kept a stale state (it relied on a change signal that Quickshell did not send), so the next lock
drew an invisible UI (grey) and `lock-stop` refused because it believed the screen was still locked. The controller now keeps its own
record of the lock, cleans up itself at unlock, and every lock starts from a clean state.
- `kurenai-ctl lock-status` / `validate` tell you when the state is stale (you are on the desktop but the locker says "locked").
- `kurenai-ctl lock-reset` (run inside your graphical session) clears it: removes the re-lock flag and restarts the locker.
- The supervisor refuses to start without `WAYLAND_DISPLAY` (a TTY) and exits when its Wayland session is gone, so a leftover
  supervisor can no longer crash-loop or block the next session's supervisor.
- hypridle was never the problem: `hypridle -v` showed it receiving the logind lock, running `lock_cmd`, and Hyprland confirming the lock.
